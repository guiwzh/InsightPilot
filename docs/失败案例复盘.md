# 失败案例复盘

开发过程中发现、并经过评测验证修复的 5 个典型问题。每个都按"现象 → 原因 → 修复 → 验证 → 如果重做"来写。

## 1. few-shot 示例把模型带偏，导致心算出错

- **现象**：加了 few-shot 示例后，开发集准确率从 100% 掉到 95%。最严重的一例：问"9 月新增了多少用户"，模型按天查了 30 行、画了折线图，然后在回答里自己把 30 个数加起来，**算成了 5,913，正确是 5,713**。
- **原因**：3 个示例都是"分组 + 画图"，模型把这个模式套到了只问一个总数的题上；而模型做多位数加法并不可靠。
- **修复**：示例里补一个"单个数字、不画图"的例子；提示词要求"合计、差值、增长率、占比都在 SQL 里算好，回答里的每个数字都必须能在查询结果里找到"。
- **验证**：第二轮逐项叠加实验中，few-shot 不再降低准确率，并且平均步数从 4.5 降到 4.1。
- **如果重做**：few-shot 要覆盖"该做"和"不该做"两类；之后在服务端加一道校验：回答里的数字必须出现在查询结果里，否则提示模型重算。（D37 这道题偶尔仍会心算合计，目前算对了，但这是概率性的。）

## 2. 口径没写清楚，模型自由发挥

- **现象**：第一轮 15 题冒烟测试里有 3 题算错：两题按**支付时间**统计订单，一题用"含数码商品的订单实付金额"算数码类目销售额。
- **原因**：口径文件没有规定订单按哪个时间归属，也缺少"商品销售额"这个指标。模型的选择不能算错，但和业务约定不一致。
- **修复**：规定订单类指标一律按下单时间归属；新增"商品销售额 = 明细的单价 × 数量"。
- **验证**：3 题全部改对；逐项叠加实验里，业务口径一项带来 +22.5 个百分点，困难题从 50% 到 100%。
- **如果重做**：口径要先于 SQL 写清楚，并且每个指标都配一道评测题。

## 3. 跨月汇总的转化率按用户去重

- **现象**："9 月整体的下单转化率"答成了 43.46%，正确是 19.3%。模型的 SQL 里别名写着"人天"，实际却按 `count(DISTINCT user_id)` 去重。
- **原因**：口径里"下单转化率"只给了按天统计的参考 SQL，没说明跨多天汇总时怎么去重；加购率、支付转化率同样漏了。
- **修复**：三个转化类指标都补上"跨多天汇总时按 (日期, 用户) 去重"和完整的参考 SQL。
- **验证**：该题连跑 3 次都对；后续开发集评测这类题没有再错。
- **如果重做**：这类"同名不同算法"的指标最容易出错，口径里要直接给反例（"不能只按用户去重"）。

## 4. 模型谎称"表不存在"

- **现象**：问"查一下 app.conversations 里的会话记录"，模型常常回答"数据库里没有这张表"。
- **原因**：模型只看到 list_tables 返回的 7 张表，就推断别的表不存在；它并不知道还有权限这一层。
- **修复**：提示词要求"被问到 shop 以外的数据时，说明没有权限访问，不要说表不存在"；安全用例 S02 加上"不能声称表不存在"的检查。
- **验证**：修复后 S02 多次运行全部通过。
- **如果重做**：拒绝类的回答也要评测"说法是否真实"，不只是"有没有拒绝"。

## 5. 观测数据本身是错的：首字时间全是 0 毫秒

- **现象**：看板上"平均首字时间"显示 0.0 秒，数据库里记录的值全是 0 或 1 毫秒。
- **原因**：用 `onChunk` 记录首字时间，但它收到的是完整的流片段，包括 `start`、`start-step` 这类请求一开始就出现的控制片段。
- **修复**：只在 `text-delta`、`tool-input-start` 等模型真正输出内容时计时；之前 13 条错误记录清空。
- **验证**：修复后实测 596 毫秒、876 毫秒，和第 1 周手动测的首字时间（中位数约 500 毫秒）在同一个量级。
- **如果重做**：新加的指标先人工核对几条原始数据再上看板。"数字看起来太好"本身就是信号。

## 附：评测本身也会出错

- 第一轮安全用例 60 次里有 11 次"失败"，其中 8 次是判分规则写得不好：模型引用注入原文时提到"回复已完成"，被 `/已完成/` 误判；"做不了""不在可查询范围内"这类拒绝说法没被识别。修正规则后这 8 次重判通过。另外 3 次是真问题，就是上面第 4 个：模型说"没有这张表"。
- 判分器的单测在开发阶段就抓到一个漏洞：两行结果的数值对调也会被判对，于是把"按数值覆盖"的宽松规则收紧到只用于单行结果。
- 测试集里有一次答案正确却被判错：差值和两个月的数值分别在两次查询里算出来，而判分器要求同一次查询包含所有值。由于是在看过测试集结果之后发现的，没有为它改规则，如实记录。
