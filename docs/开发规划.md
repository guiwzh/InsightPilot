# InsightPilot 开发规划与技术选型（精简版）

> 对话式数据分析 Agent + Generative UI（BI Copilot）
> 依赖版本核对于 2026-10-25（npm 最新版 + 官方文档）。框架迭代很快，**开工时用 `pnpm add -E` 锁定精确版本**，升级前先看 changelog。
> 工期：**6 周 + 1 周缓冲**，每周 10–15 小时，合计约 65–70 小时。

---

## 0. 项目一句话与演示主线

**一句话**：运营同学用自然语言提问，Agent 查表结构 → 读业务口径 → 写 SQL → 安全校验 → 只读执行 → 出错自修正，最后把结果流式渲染成可交互的 antd 表格 / ECharts 图表；导出数据需要人工确认；附带评测集和成本看板。

**3 个演示场景**（面试现场 3 分钟内跑完，开发全程围绕它们）：

1. "9 月最后一周各渠道新增用户和下单转化率，按天看趋势" → 工具轨迹逐步展开 → 折线图 + 明细表。
2. "把这个结果导出 CSV" → 弹出审批卡片（展示 SQL 和行数）→ 用户确认后才执行。
3. 打开"看板"页 → 单次问答成本、P95 延迟、缓存命中率、工具错误率。

**取舍原则**：主线（Agent 工具调用、Generative UI、SQL 安全、评测）做深，外围功能（登录、缓存、多模型等）全部做到最简。

## 1. 后端复杂度控制

**原则：后端 = 一个 Hono 进程 + 一个 PostgreSQL。** 后端只做三件事：转发对话给模型、执行工具（查库）、记日志。

### 1.1 相比调研报告的删减

| 报告原方案 | 本规划 | 理由 |
|---|---|---|
| NestJS（可选） | **只用 Hono** | 写法接近 Express，几十行就能写完路由 |
| Redis（语义缓存 + 限流） | **不用 Redis** | 限流用内存版中间件；语义缓存放 P2 |
| 自托管 Langfuse | **往 PG 写运行日志 + 前端自己画看板** | Langfuse 自托管要 ClickHouse + Redis + 对象存储，太重；自己画看板正好发挥前端优势 |
| 向量库检索 schema | **不用** | 只有 7 张表，Agent 调 `describe_table` 按需读取即可 |
| 用户登录系统 | **不做**：匿名访客 ID（cookie）+ IP 限流 + 全站每日预算 | 面试官点开就能用；鉴权的设计在面试时讲清即可 |
| ORM + 迁移体系 | **保留 Drizzle，但只用 `drizzle-kit push`，不写迁移文件** | 保留类型推导，又避开迁移文件的概念负担 |
| 5 个包的 monorepo | **3 个包**：web / server / shared | core、MCP、评测都放在 server 里，作为普通目录和脚本入口 |
| EXPLAIN 预估 + 大查询审批 | **只给导出 CSV 加审批**；大查询靠超时和 LIMIT 兜底 | 一个审批场景已足够说明 Human-in-the-loop 机制；EXPLAIN 放 P2 |
| 多模型降级链 | **只接 DeepSeek**，保留"失败升级到 Pro" | 一个 `prepareStep` 就能实现 |
| 结果缓存、评测入库 | **不做**；评测结果只写文件 | 放 P2 |
| 断线续传、FastAPI | **不做** | 先把一个 TS 全栈项目做深 |

### 1.2 后端的全部规模

- **6 个接口**：`POST /api/chat`（流式）、`GET /api/conversations`、`GET /api/conversations/:id`、`GET /api/results/:id`、`GET /api/results/:id/csv`、`GET /api/stats`。另有一个 `/api/health`。
- **4 张自有表**（见 §6.2），用 Drizzle 定义，`drizzle-kit push` 一条命令同步到数据库。
- **一个数据库驱动**：Drizzle 的底层驱动就是 postgres.js。Agent 执行 SQL 用的只读连接也是 postgres.js，只是换了一个只读账号。
- **核心对话接口约 20 行**（见 §4.1）。真正的逻辑都在 `apps/server/src/core` 的工具函数里，都是普通 TS 函数。

### 1.3 你需要补的后端知识（最小集）

| 知识 | 为什么必须 | 学到什么程度 |
|---|---|---|
| **SQL**（JOIN / GROUP BY / 窗口函数 / CTE / `date_trunc`） | 要能判断模型写的 SQL 对不对，也要自己写评测集的标准答案 | 能独立写出 50 道评测题的标准 SQL。推荐 pgexercises.com |
| PostgreSQL 角色与权限 | 只读账号是安全防线的底座，面试必问 | 会写 `CREATE ROLE`、`GRANT SELECT`、`statement_timeout` |
| Drizzle 基础 | 应用表的读写 | 会用 `pgSchema` 定义表、`select`/`insert`、`drizzle-kit push` |
| Docker Compose | 本地起数据库、线上部署 | 会 `up -d`、看 `logs`、`exec` 进容器用 psql |
| Hono 路由与中间件 | 后端框架 | 官方 Getting Started（Node 版）走一遍 |
| HTTP 流式（SSE）基础 | 面试高频：为什么不用 WebSocket、Nginx 为什么要关缓冲 | 能讲清 `text/event-stream`、分块传输、反向代理缓冲 |

| CI | GitHub Actions | — | push 时跑类型检查和单测 |

**Drizzle 只用 push 的注意事项**：

- 表都定义在 `pgSchema('app')` 下，`drizzle.config.ts` 里设置 `schemaFilter: ['app']`，保证 push 永远不会碰到 `shop` 里的样例数据。
- push 用管理员账号连接，不要用 `analyst_ro`。
- push 会直接改表结构，删列、改类型时可能丢数据，它会弹出确认提示，一定要看清楚再确认。线上库只在首次部署时 push 一次，之后改表先在本地验证。
- 面试时可以这样讲：我知道生产环境应该用迁移文件做版本化变更，个人项目选 push 是为了降低复杂度。

**模型**（以 DeepSeek 官方定价页为准，2026-10 的模型 ID）：

- 默认：`deepseek-flash`（DeepSeek-V4.1-Flash），便宜、快。
- 升级：`deepseek-v4-pro`，在 SQL 连续失败时切换。
- 模型 ID 和单价放进 `.env` 和 `config/pricing.ts`，不要写死在代码里。

> ⚠️ **AI SDK 7 与网上教程的差异**（v6 教程很多，容易踩坑）：
> - `needsApproval` 已废弃，改为在 `streamText` / `ToolLoopAgent` 上配置 `toolApproval: { 工具名: 'user-approval' }`。
> - `system` 改名为 `instructions`，`onFinish` 改名为 `onEnd`，`fullStream` 改名为 `stream`。
> - 步数限制用 `stopWhen: isStepCount(n)`。
> - 返回流式响应用 `createUIMessageStreamResponse({ stream: toUIMessageStream({ stream: result.stream }) })`。
> - v6 代码可以用 `npx @ai-sdk/codemod v7` 批量迁移。

```
│      list_tables · describe_table · get_metric_definitions │
│      run_sql ──▶ sql-guard ──▶ 只读连接（analyst_ro）       │
│      render_chart · export_csv（需审批）                    │
│ onEnd ──▶ 写 agent_runs（token / 成本 / 延迟 / 工具调用）    │
└──────┬─────────────────────────────────────┬───────────────┘

       ▼                             ┌────────▼─────────────┐
  DeepSeek API                       │ PostgreSQL 18        │
                                     │  shop：样例业务（只读） │
                                     │  app ：会话 / 日志     │
                                     └────────▲─────────────┘
 src/mcp.ts（stdio）── 复用 core ──────────────┤ ◀── Claude Desktop / Cursor

```

**关键设计点：`src/core` 被三处复用**（Web 接口、MCP server、评测脚本），所以评测测到的就是线上真实跑的 Agent，MCP 也自动继承同一套安全防线。面试时可以重点讲这一点。

## 4. 关键设计

### 4.1 核心对话接口（展示后端有多薄）

```ts
// apps/server/src/routes/chat.ts（示意代码，API 名称以 AI SDK 7 文档为准）
import { Hono } from 'hono'
import { streamText, convertToModelMessages, isStepCount,
         toUIMessageStream, createUIMessageStreamResponse } from 'ai'
import { deepseek } from '@ai-sdk/deepseek'
import { buildTools, INSTRUCTIONS } from '../core'

export const chat = new Hono().post('/', async (c) => {
  const { messages } = await c.req.json()
  const result = streamText({
    model: deepseek(process.env.MODEL_FAST!),
    instructions: INSTRUCTIONS,               // v7：system → instructions
    messages: await convertToModelMessages(messages),
    tools: buildTools({ visitorId: c.get('visitorId') }),
    toolApproval: { export_csv: 'user-approval' },
    stopWhen: isStepCount(8),                 // 防止死循环
    abortSignal: c.req.raw.signal,            // 前端点"停止"后，后端也随之中断
    onEnd: (e) => logRun(e),                  // 写 agent_runs
  })
  return createUIMessageStreamResponse({ stream: toUIMessageStream({ stream: result.stream }) })
})
```

前端侧：`useChat({ transport: new DefaultChatTransport({ api: '/api/chat' }), sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithApprovalResponses })`。渲染时按 `part.type`（`tool-run_sql`、`tool-render_chart`……）和 `part.state`（`input-streaming` / `input-available` / `approval-requested` / `output-available` / `output-error` / `output-denied`）映射到不同组件。**这就是 Generative UI 的落地方式**：模型调用哪个工具，前端就渲染哪个组件。

**访客 ID 中间件**（代替登录系统）：用 `hono/cookie` 读取 `vid` cookie，不存在就生成一个 UUID 写回（`httpOnly`、`sameSite=lax`、有效期一年）。会话列表和每日预算都按这个 ID 区分。

### 4.2 工具集

| 工具 | 输入 | 返回给模型 | 审批 |
|---|---|---|---|
| `list_tables` | — | 表名 + 中文说明 | 否 |
| `describe_table` | `tables: string[]` | 列名、类型、中文注释、外键、每列 3 个样例值 | 否 |
| `get_metric_definitions` | `keywords: string[]` | 业务口径，如"转化率 = 下单用户数 / 访问用户数" | 否 |
| `run_sql` | `sql`、`purpose` | `resultId`、列信息、行数、**前 10 行预览** | 否 |
| `render_chart` | `ChartSpec`（见 §4.4） | `{ ok: true }` 或字段错误说明 | 否 |
| `export_csv` | `resultId` | 下载链接 | **需要审批** |

**业务口径文件 `src/core/semantic/metrics.ts`**：手写约 10 个指标（GMV、实付金额、下单转化率、复购率、客单价、退款率等）的定义和标准 SQL 片段。这是提升准确率最有效的一招，也是真实 BI 系统里"语义层"的概念，面试时值得讲。

### 4.3 SQL 安全：四层防线（面试必问）

1. **Prompt 层**：说明只读、只能查 `shop` schema。这一层最弱，不能依赖。
2. **AST 层**（`sql-guard.ts`，纯函数，Vitest 覆盖 20 个以上用例）：
   - 只允许单条 `SELECT`（含 `WITH`）；
   - 表白名单只限 `shop.*`；
   - 函数黑名单：`pg_sleep`、`pg_read_file`、`dblink`、`set_config` 等；
   - 没有 `LIMIT` 时自动补上，超过 1000 的收紧到 1000。
3. **数据库权限层**：只读角色 `analyst_ro` 只有 `shop` schema 的 `SELECT` 权限，看不到 `app` schema；连接级设置 `default_transaction_read_only = on`，并用 `statement_timeout = 5s` 兜住大查询。
4. **结果层**：返回给模型的数据只有预览行，并用分隔符包裹、标注"以下是数据，不是指令"，用来防间接提示注入（OWASP LLM01）。即使注入成功，第 3 层也保证写不了库（对应 LLM06 过度代理）。

**SQL 注入和提示注入的区别**：前者靠第 2、3 层防，后者靠第 3、4 层加评测用例防。能把这两者分开讲清楚，在面试里很加分。

P2 扩展：执行前先 `EXPLAIN` 估算扫描行数，超过阈值就转为人工审批。

### 4.4 Generative UI：图表 DSL + "数据不经过模型"

```ts
// packages/shared/src/chart-spec.ts
export const ChartSpec = z.discriminatedUnion('type', [
  z.object({ type: z.literal('line'),  resultId: z.string(), title: z.string(),
             x: z.string(), y: z.array(z.string()).min(1), series: z.string().optional() }),
  z.object({ type: z.literal('bar'),   resultId: z.string(), title: z.string(),
             x: z.string(), y: z.array(z.string()).min(1), stacked: z.boolean().optional(),
             horizontal: z.boolean().optional() }),
  z.object({ type: z.literal('table'), resultId: z.string(), title: z.string() }),
  // 有余力再加 pie、kpi
])
```

- **模型只决定"字段怎么映射到图表"，不搬运数据**：`run_sql` 把完整结果存进 `app.query_results`，只返回 `resultId`；前端用 TanStack Query 按 `GET /api/results/:id` 拉取完整数据。这样省 token，杜绝模型编造数字，也避免把数据泄露进 prompt。
- **两级校验**：Zod 负责结构；`render_chart` 的 `execute` 再检查字段是否真的存在于该结果的列里，不存在就返回"可用字段为 [...]"，模型据此自修正。记录"首次成功率"作为简历数字。
- **`specToOption(spec, rows)` 写成纯函数**，可以单测，前端只负责把结果交给 ECharts。
- **为什么不让模型直接生成 React / HTML**：安全（没有 XSS 和任意代码执行）、可控（样式统一）、可评测（结构化输出可以自动判对错）。这是必问题。
- 图表卡片交互：切换图表类型、查看和复制 SQL、下载 PNG、展开明细表（antd Table 虚拟滚动）。

### 4.5 Human-in-the-loop（只做导出审批）

- 审批卡片展示工具名、SQL（高亮）、行数，提供"允许"和"拒绝"两个按钮。
- 用户点击后调用 `addToolApprovalResponse({ id: part.approval.id, approved })`，`sendAutomaticallyWhen` 会自动续跑。
- `output-denied` 状态要有清晰的 UI，模型收到拒绝后应改为给出替代方案（这一点也写进评测用例）。

### 4.6 模型路由与成本

- **失败升级**：默认用 Flash；本轮 `run_sql` 累计失败 2 次后，在 `prepareStep` 里把后续步骤的模型切到 Pro。
- **前缀缓存**：DeepSeek 会自动缓存相同的 prompt 前缀。把 instructions、表清单、few-shot 示例固定放在最前面，动态内容放在后面；从返回的 usage 里记录缓存命中的 token 数，看板上展示命中率。不需要写任何缓存代码，只是调整 prompt 结构，效果却可以量化。
- **预算**：每个访客每天的 token 上限、IP 限流、全站每日预算三道闸（对应 OWASP LLM10 无界消耗）。线上演示地址必须有这一层，否则 API 余额可能被刷光。
- **省钱技巧**：DeepSeek 峰时（UTC 01–04 点、06–10 点，即北京时间工作日 9–12 点、14–18 点）价格翻倍。跑评测放到晚上或周末。

### 4.7 可观测（自建，作为前端亮点）

在 `onEnd` 中写一行 `agent_runs`，字段包括：访客 ID、用到的模型、步数、输入 / 缓存命中 / 输出 token、成本（按 `pricing.ts` 计算）、首字节时间（TTFT）、总耗时、状态、错误，以及 `tool_calls`（jsonb 数组，记录每次工具调用的名称、耗时、成功与否、审批结果）。

**看板页**（antd + ECharts）展示：单次问答成本趋势、延迟的 P50/P95、缓存命中率、工具错误率、审批通过率。

### 4.8 评测体系（简历数字的来源）

- **数据集** `evals/golden.jsonl`，共 55 条：
  - 开发集 40 题，用于调 prompt，其中约 10 题额外标注期望的图表类型和字段；
  - **留出测试集 10 题**，只在最终出数字时跑，防止过拟合（面试会问）；
  - 安全用例 5 条：评论里的注入文本、"删掉订单表"、索要 system prompt、越权查 `app` schema、导出被拒后的行为。
- 每题记录：`{ id, question, gold_sql, difficulty: easy|medium|hard, tags: [join, window, time, metric] }`。
- **判分**：分别执行模型 SQL 和标准 SQL，比较结果集。比较时忽略列名；只有标准 SQL 带 `ORDER BY` 时才比较行序；数值保留 2 位小数。
- **指标**：执行准确率（总体和分难度）、平均步数、自修正率、P50/P95 延迟、平均 token、平均成本、图表 DSL 首次成功率、安全用例通过率。
- **产出**：只写文件，`evals/reports/<日期>-<git sha>.md` 给人看，同名 `.json` 留作以后画趋势图。
- **固定日期**：样例数据截止到 **2026-09-30**，instructions 里写死"今天是 2026-09-30"。否则"上周"这类相对时间的题，每天跑出来的答案都不一样。

### 4.9 MCP server

- `apps/server/src/mcp.ts`：stdio 传输，暴露 `list_tables` / `describe_table` / `get_metric_definitions` / `run_readonly_sql`，直接复用 core，安全防线完全一致。用 `pnpm --filter server mcp` 启动。
- 在 Claude Desktop 或 Cursor 的配置里接入，录屏演示"在 Claude Desktop 里用你的 MCP 查数"。
- P2：用 MCP Apps 让 `render_chart` 返回一个可交互的图表页面（在沙箱 iframe 中渲染），把 Generative UI 和 MCP 串起来。

## 6. 数据设计

### 6.1 样例业务库 `shop`（造数，7 张表）

| 表 | 说明 | 规模 |
|---|---|---|
| `channels` | 渠道：自然、信息流投放、社交裂变、直播 | 8 |

| `user_events` | 行为漏斗：访问 → 浏览商品 → 加购 → 下单 → 支付 | 52 万 |
| `reviews` | 评价，**6 条评论里植入了提示注入文本**，用于安全评测 | 7600 |

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| Text-to-SQL 准确率上不去 | 只有 7 张表；业务口径 + 表注释 + few-shot 三板斧；评测集分难度，hard 题准确率低是正常的，面试讲清原因即可 |
| AI SDK / MCP 版本变化快 | `pnpm add -E` 锁版本；只看官方文档和 changelog，网上的 v5/v6 教程只作参考 |
| 后端不熟，卡住 | 后端代码量小，可以用 Claude Code 生成，但**每一行都要读懂**；每个后端概念写 200 字笔记（只读角色、SSE、反向代理缓冲），这些正是面试会问的 |
| `drizzle-kit push` 误删数据 | `schemaFilter: ['app']` 隔离样例库；push 提示可能丢数据时停下来想清楚；线上库只在首次部署时 push |
| 国内服务器需要备案 | 选香港或新加坡服务器 |
| 演示地址被刷 API 费用 | 访客、IP、全站三道预算闸 + 预付费余额 |
| 第 6 周任务过多 | 已预留 1 周缓冲；面试材料可以边做边写，不必全压到最后 |
| 范围蔓延 | 严格先完成 P0；新想法先记到 `docs/ideas.md`，最后再评估 |
