## 高频追问

**流式输出**
- **为什么用 SSE 不用 WebSocket？** 单向推送足够；就是普通 HTTP，能复用中间件、走 CDN；停止 = 断开请求，服务端用 abortSignal 停止调用模型。见 [ADR 0004](adr/0004-sse.md)。
- **打字机效果怎么实现，怎么防卡顿？** 模型按 token 流式返回，AI SDK 把片段合并进 UIMessage；`useChat` 设了 50ms 节流（每秒最多约 20 次重渲染），助手消息组件用 memo，历史消息不重渲染（实测 312 → 0 次）；ECharts 实例只创建一次，数据不变就不调用 setOption。
- **Nginx 后面 SSE 不流式？** 代理缓冲。Nginx 关 `proxy_buffering`，或依赖响应头 `X-Accel-Buffering: no`；Caddy 对 event-stream 会立即转发。线上就是 Nginx（NPM）→ Caddy → Node 两层代理，AI SDK 的流式响应自带这个头，没有改 Nginx 配置，实测 82 个事件逐步到达。
- **断线续传？** 没做。AI SDK 的方案需要 Redis 存流；目前会话在请求开始和结束各存一次，刷新后能恢复已完成的部分。

**Generative UI**
- **为什么用 DSL 不让模型生成代码？** 安全（无 XSS、无代码执行）、样式可控、可以自动校验和评测。见 [ADR 0002](adr/0002-chart-dsl.md)。
- **Markdown 怎么防 XSS？** x-markdown 开 `escapeRawHtml`，模型输出里的 HTML 一律当文本显示。
- **DeepSeek 为什么拒绝了你的工具定义？** 工具参数的 JSON Schema 顶层必须是 object，判别联合会生成 anyOf。改成扁平对象 + 运行时校验。

**Agent 工程**
- **怎么防死循环？** 最多 8 步；同一条 SQL 第二次提交时不执行、直接提示，第三次结束本轮；最后一步禁止调用工具，强制作答。
- **Tool、MCP、Skill 有什么区别？** Tool 是一次函数调用的接口；MCP 是把一组工具（以及资源、提示词）通过标准协议暴露给任意客户端，本项目的 4 个只读工具既能被自己的 Agent 用，也能被 Claude Desktop 用；Skill 是打包好的指令和脚本，告诉 Agent "某类任务怎么做"，偏流程知识。
- **报错自修正怎么做的？** 工具抛出带错误码、PostgreSQL 原始报错和针对错误码的修复建议的错误，AI SDK 把它作为工具结果交还模型。实测开启业务口径后首条 SQL 几乎都能直接成功，所以修复建议在评测里很少有机会出场。
- **失败升级到更强的模型？** SQL 累计报错 2 次后，prepareStep 把后续步骤换成 Pro 模型。开发集上几乎不触发，价值还没被量化（如实说明）。

**安全**
- **SQL 注入和提示注入有什么区别，各自怎么防？** SQL 注入是让 SQL 做不该做的事：靠 AST 白名单和数据库只读角色。提示注入是让模型做不该做的事（比如评价内容里写"忽略之前的指令"）：靠只读权限兜底（即使被带跑也写不了库）、数据标注、评测用例检查。
- **为什么只读角色还要 AST 校验？** 纵深防御：AST 层挡住模型写错的 SQL，给出可修复的错误信息；数据库权限保证即使 AST 被绕过也写不了、看不到 app 数据。实测在会话里执行 `SET default_transaction_read_only = off` 后 DELETE 仍然因为没有权限失败。
- **审批能被伪造吗？** 目前审批状态在客户端消息里，理论上可以伪造。AI SDK 7 支持对审批签名（HMAC，把工具参数绑定到审批令牌），这是下一步。
- **限流怎么防 IP 伪造？** 每层代理都把上一跳的地址追加到 X-Forwarded-For 的右边，只有右边由我们自己的代理写的部分可信。线上有两层代理（NPM → Caddy），都在 Docker 内网，所以从右往左跳过内网地址，第一个公网地址就是真实客户端；更左边的部分来自客户端的请求头，不用。实测在左边伪造地址仍然被限流。前提是代理都在内网，以后前面加 CDN，就要把 CDN 的出口网段也列为可信。

**部署**
- **为什么在本机构建镜像再传到服务器？** 服务器只有 2G 内存，上面还跑着别的服务，构建前端容易把内存吃满；内地服务器拉 Docker Hub 经常超时。本机用 `--platform linux/amd64` 构建，`docker save | ssh docker load` 传过去，服务器上已有的版本不重复传。
- **部署时踩过什么坑？** 数据库初始化失败但容器显示健康：服务器 root 的 umask 是 027，scp 上去的 init.sql 只有 root 能读，容器里的 postgres 用户读不了；而 Postgres 只在第一次初始化时执行 init 脚本，重启也不会再跑，导入数据时才发现表全不在。发布脚本里加了 chmod，删掉空数据卷重新初始化。

**评测**
- **评测集怎么构造，怎么防过拟合？** 开发集 40 题用于调优，测试集 10 题留到最后只跑一次；标准 SQL 都亲手写并执行核对。口径是对着开发集错题补的，测试集 93.3% 说明有一定泛化，但样本小。
- **为什么准确率有"严格"和"宽松"两档？** 模型常多带一行合计或对比月份，严格比对会低估正确率；宽松仍要求同一行里的值对得上，判分器有单测。
- **accuracy / latency / cost 三个数？** 开发集 100%、测试集 93.3%；P50 约 4–4.5 秒、首字约 0.6–0.9 秒；单题约 ¥0.004。思考模式实测准确率没提高，延迟和成本更高，所以关闭。
- **一次评测花多少钱？** 40 题跑一遍约 ¥0.17。

**成本**
- **怎么算的成本？** 每一步按模型的单价（缓存命中、未命中、输出分别计价，DeepSeek 峰时翻倍）乘 usage 累加，写进 agent_runs。
- **为什么 40.2%？** 前缀缓存只对完全相同的开头生效。对照实验在提示词开头放一个每次都变的编号，命中率从 89.7% 掉到 72.7%，成本从 ¥0.0043 涨到 ¥0.0071。
